# Game engineering

tibo.dog runs at 60 fps with 500 enemies on a mid-range phone inside an X post, and its first download is about 124 KB gzipped. It is fully deterministic: the server replays a run to verify a score. Our games are smaller, and should be built the same way.

## Structure
- **Pure simulation in `tools/<slug>/lib/`:** `createGame(seed, level)` and `stepGame(state, input, dt)`, with no DOM, no `Math.random` (use `makeRng(seed)` from `shared/game-core.ts`) and no `Date.now`. The React component only feeds input, draws and plays sounds.
- **Fixed step:** run through `useGameLoop` (60 steps a second, paused when hidden). The same seed and inputs give the same result on every phone, so links replay and tests can check it.
- **Levels are data:** put them in `lib/levels.ts`, generated by a script or written by hand. A test proves each one solvable or fair: a solver, or a headless bot.

## Hot paths (`*.hot.ts`)
- Code that runs every frame or every step lives in files ending `.hot.ts`, such as `lib/step.hot.ts` and `lib/draw.hot.ts`.
- **In a `.hot.ts` file, never:**
  - write object or array literals in the loop body;
  - define closures or arrow functions per frame;
  - call `new` per frame;
  - use `.map`, `.filter` or spread in the loop;
  - concatenate strings or build template literals for canvas text per frame (cache them).
- Use preallocated typed arrays or object pools created at setup, mutate in place, and cache gradients and pre-render static layers offscreen.
- `npm run lint:games` (`scripts/lint-games.mjs`) checks these rules, and the repo's other bans. Fix the code, never the rule.

## Every bug becomes a rule
When you find a bug class (a statechart rule that broke, a mistake a test caught, a review finding), add a check that would have caught it:
- a node test in the game, when it's specific to that game;
- a rule in `scripts/lint-games.mjs`, when any game could repeat it. Examples: an AudioContext outside the kit, `navigator.vibrate` directly, `Math.random` in `lib/`, `setTimeout` without clearing, a held-input flag with no blur release, a literal ড় inside a regex range.

Note the rule in your report.

## Budgets
- **First load for a game page:** keep the game's own client JS small. Draw art in code (SVG or canvas) and use no image files except the generated tile and share images.
- `npm run budget` (`scripts/budget.mjs`) fails when a route's first-load JS grows past its budget. Never raise a budget to make a build pass without saying why.

## Difficulty by bots
- Write a headless bot in the test that plays `stepGame` the way a person would. Give it human reaction time (0.25–0.35 s), aim error, and sometimes a wrong choice.
- Tune each level so the target player wins at the intended rate. For example, a casual bot clears level 1 99% of the time and a strong bot clears the last level about 50% of the time.
- Assert those rates in tests over many seeds.

## Audio and art
- All sound comes through `shared/game-sound.ts` (`sfx`, `tone`, `hiss`, `loop`, with `pitch` and `set`). Songs, if any, are written as note data in code and change with the stage while keeping the melody going.
- All art is code: SVG or canvas drawn from shared palettes in `lib/art.ts`, pre-rendered once, and drawn as cached bitmaps.

## Tests every game has
- **Determinism:** same seed and inputs give the same state.
- **Rules:** win, lose, scoring, stars and level unlock.
- **Fairness:** every level is solvable, or the bot clears it at its target rate.
- **Statechart paths:** each bug path replayed against the pure logic.
- **Link parsing:** hostile input is rejected; old link formats still open.
- **Content limits:** SEO lengths and Bangla NFC.
